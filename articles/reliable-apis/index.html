Designing Reliable APIs: Idempotency, Retries, and Error Handling

Practical patterns for building APIs that behave predictably when clients retry requests, networks fail, or dependencies become temporarily unavailable.

By Moazzam Rafi · Technical article · 8-minute read

An API can work perfectly under normal conditions and still fail users when something unexpected happens. A network connection may drop after a server has processed a request. A downstream service may respond too slowly. A client may retry because it cannot tell whether the original operation succeeded.

Reliable API design is not simply about returning a successful HTTP response. It is about defining predictable behavior during failures, preventing unintended duplicate operations, and making recovery understandable for clients.

Three useful building blocks are idempotency, controlled retries, and consistent error handling.

1. Understand the uncertain outcome problem

Imagine an online service that accepts a request to create an order. The server creates the order, but the network connection drops before the response reaches the client.

From the client's perspective, the result is unknown. If it sends the request again, the service might create a second order unless it has a way to recognize the repeated operation.

Client sends create-order request
↓
Server creates the order successfully
↓
Response is lost due to a network failure
↓
Client cannot determine the outcome and retries

The key challenge: a failed response does not necessarily mean the operation failed.

This distinction matters for any operation that creates or changes state, including orders, payments, bookings, and resource creation.

2. Use idempotency to prevent duplicate operations

An operation is idempotent when repeating it with the same intended input produces the same intended effect as performing it once. HTTP defines idempotent methods, but application APIs may also implement idempotency for operations such as creating an order or initiating a payment.

One common approach is an idempotency key. The client creates a unique key for one logical operation and reuses that key when retrying the same operation. 

POST /v1/orders
Idempotency-Key: order-request-8f31

{
  "productId": "item-204",
  "quantity": 1
}

The server uses the key to identify repeated requests. A typical implementation stores the key, a request fingerprint, the operation status, and the result associated with that key.

A typical processing flow

  1. Receive the request and validate its inputs.
  2. Look up the idempotency key within the correct client or account scope.
  3. If the key is new, safely register the operation and process it.
  4. If the same key and same request were already completed, return the saved result.
  5. If the same key is reused with different input, reject the conflicting request.
  6. If the original operation is still running, return a documented in-progress response or follow a defined waiting policy.
Important: Checking for a key and recording it must be concurrency-safe. Otherwise, two simultaneous requests may both pass the check and perform the operation. The design also needs a clear policy for key expiration, incomplete operations, and recovery after a crash.

3. Design retries carefully

Retrying can help recover from temporary failures, but uncontrolled retries can amplify an outage. If many clients repeatedly call an overloaded dependency, they can increase its load precisely when it is least able to handle it.

A resilient retry policy should define:

  • Retryable failures: distinguish temporary network errors, timeouts, and selected server errors from permanent validation or authorization failures.
  • Attempt limits: set a maximum number of attempts.
  • Exponential backoff: increase the delay between attempts.
  • Jitter: add randomness to avoid many clients retrying at the same time.
  • Deadlines: stop retrying when the request's overall time budget has expired.
  • Idempotency: use it when retrying operations that may change state.

For example, a client might use this illustrative schedule:

Attempt 1: immediately
Attempt 2: after about 200 ms
Attempt 3: after about 400 ms
Attempt 4: after about 800 ms

These are example delays, not universal defaults. Production policies should account for service latency, retry budgets, server-provided guidance such as Retry-After, and the impact of the operation.

4. Make error responses predictable

Clients need enough information to decide whether to correct a request, authenticate again, wait and retry, or investigate an unexpected failure. Consistent error formats make that decision easier. 

{
  "error": {
    "code": "RESOURCE_CONFLICT",
    "message": "The request conflicts with the current resource state.",
    "requestId": "req-example-123"
  }
}

A useful error contract includes a stable machine-readable code, a clear message, and a request identifier for diagnostics. Avoid returning stack traces, secrets, internal hostnames, or other sensitive implementation details.

Use HTTP status codes consistently. For example, a malformed request may return 400, an unauthenticated request may return 401, a missing resource may return 404, and a rate-limited request may return 429. Choose status codes according to the API's documented semantics.

5. Set timeouts and protect dependencies

A request that waits indefinitely can consume connections, threads, memory, or other resources. Set explicit connection and response timeouts, and establish an end-to-end deadline that downstream calls respect.

For systems with failing dependencies, circuit breakers, concurrency limits, and load shedding can help prevent one unhealthy component from exhausting resources across the wider system. These mechanisms complement retries; they do not replace correct operation semantics.

6. Test failure scenarios, not only the happy path

Reliability improves when failure behavior is part of the test plan. In addition to normal successful requests, test scenarios such as:

  • The server succeeds but the response is lost.
  • The client sends the same idempotency key concurrently.
  • The same key is reused with a different request body.
  • A dependency times out or returns a temporary error.
  • The service crashes after recording an operation but before completing it.
  • The retry limit is reached and the client must recover.

Monitor request latency, error rates, retry volume, timeout rates, duplicate-request handling, and incomplete operations. These signals help reveal whether an API is reliable under real operating conditions.

Key takeaways

  • Design for uncertain outcomes: a lost response does not prove an operation failed.
  • Use concurrency-safe idempotency for operations that must not be duplicated.
  • Apply bounded retries with backoff, jitter, and deadlines.
  • Keep HTTP status codes and error response formats consistent.
  • Use timeouts and dependency protection to contain failures.
  • Test retries, concurrency, and partial failures explicitly.

Reliable APIs emerge from the interaction of these choices. Idempotency helps control repeated operations, retry policies help recover from transient failures, and clear error contracts let clients respond appropriately. Together, they make distributed systems easier to operate and safer to integrate.
